# settlebase コンセプト（何のためのシステムか）

settlebase の全体像の一次ソース。画面別の要件は [screen-specs.md](screen-specs.md)、
用語は [GLOSSARY](../../GLOSSARY.md) を参照。

## 一言でいうと

**会社の中のお金の動きを、記録と統制に振り切って管理するデモシステム。**
実際の銀行送金はしない。扱うのは「社内の帳簿とワークフロー」だけ —
部門予算の管理と経費精算の承認フローを、**改ざんできない・権限を分離する・
すべて監査できる** という統制パターンに絞って実装する。

本番プロダクトではなく、連載「企業で AI を安全に使って業務システムを作る」の
教材・図版である。機能の便利さではなく、統制の型（マルチテナント分離 /
maker-checker / 冪等キー / append-only 台帳 / 監査ログ）を見せることが目的。

## 登場人物と 1 ヶ月の物語（デモシナリオ）

テナント A 社のシードデータはこの物語に沿って作る。

| 登場人物 | ロール | やること |
| --- | --- | --- |
| たなか | 管理者（admin） | 部門ウォレットを作り、予算を配り、ロールを管理する |
| さとう | 開発部メンバー（maker） | 立替精算・振替を申請する |
| やまなか | 経理（checker） | 申請を確認し、承認・却下する |
| 監査役 | 閲覧（viewer） | 台帳と監査ログを読む。何も変更できない |

- **月初**: たなかが「準備金ウォレット → 各部門」の振替を申請し、承認を経て予算が配賦される
- **日常**: さとうが立替精算を申請（二重クリックしても冪等キーで 1 件）→ やまなかが承認 → 承認と同時に「開発部ウォレット → さとうのウォレット」が台帳に自動記帳される。やまなか自身の申請はやまなかには承認できない
- **訂正**: 誤った記帳に気づいたら、台帳から逆仕訳を申請 → 別の checker が承認 → 反対記帳で相殺。元の記録は消えない
- **期末**: 監査役が台帳を遡ると、すべての残高がどの記帳から生まれたか説明できる

テナント B 社は「境界の向こう側」を見せるための最小データを持つ。
テナント切替で「同じ画面なのに中身が完全に分かれている」ことを示す。

## お金のモデル（すべては振替である）

- ウォレットは部門・メンバー個人・テナント準備金（会社の金庫）の 3 種
- **すべての残高変動は「ウォレット間の複式記帳（振替）」1 種類**で表現する
  - 予算配賦 = 準備金 → 部門 / 立替精算 = 部門 → メンバー / 部門間振替 = 部門 → 部門 / 逆仕訳 = 反対向きの振替
- 記帳は承認後にのみ自動で行われる（1 トランザクション）。マイナス残高は許容しない
- 唯一の承認外エントリは、テナント開設時の準備金初期化（開設イベント）

## 6 画面と物語の対応

| 画面 | 役割 |
| --- | --- |
| 部門ウォレット | 予算の見える化（準備金を含む） |
| 振替・精算申請 | お金を動かす唯一の入口（冪等キー） |
| 承認 | 動かしてよいかの関所（maker-checker） |
| 台帳 | 動いた事実の唯一の正本（append-only・逆仕訳） |
| 監査ログ | 状態を変えた操作と認証イベントの記録 |
| ロール管理 | 誰に何をさせるかの統制 |

## 読者への公開形態（段階制）

1. **当面**: 記事のスクショ + 公開 URL（初期画面の確認まで）
2. **実装が揃ったら**: 閲覧用デモアカウント（viewer・テナント A/B 両所属）を公開し、
   読者自身がテナント切替と境界分離を体験できるようにする（別 bead で実施）

読者の自由サインアップは本格運用しない（悪用・ゴミデータ・無料枠の運用負荷）。

## やらないこと（機能境界）

- 実決済・銀行/決済 API 連携（README の Out of Scope どおり）
- 会計ソフト連携・仕訳エクスポート
- 通知（メール / Slack）
- 多通貨（JPY のみ）
- 締め処理・会計期間の概念
- 証憑ファイルの実体保存（UI はダミー添付）
- 高度な検索・レポート / 分析ダッシュボード
- モバイル対応（デスクトップファースト。将来は承認画面から縦切り）
