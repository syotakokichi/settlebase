# 2026-07-20 主要6画面のUI設計（Claude Design）

マルチテナント社内精算基盤デモの主要 6 画面（部門ウォレット / 振替・精算申請 /
承認 / 台帳 / 監査ログ / ロール管理）を Claude Design で設計した記録。
成果物は [docs/design/](../design/)（ワイヤー PNG 8 枚・台帳の静的 HTML・
[screen-specs](../design/screen-specs.md)・[design-system](../design/design-system.md)・
[concept](../design/concept.md)）。

## 1. ツール選定: Pencil.dev → Claude Design へ変更

当初計画は Pencil.dev だったが、着手時の比較（Pencil / Claude Design / HTML モック直書き）で
**Claude Design（Beta）主軸**に変更した。決め手は 4 点。

1. デザインシステム機能があり「デザインの決め方」自体を記録・素材化できる
2. HTML エクスポート + Claude Code ハンドオフで設計→実装の二度手間が小さい
3. .pen 形式は読者が開けないが、エクスポート HTML / PNG は公開 repo で誰でも見られる
4. Claude Design × Claude Code 連携の実践記録としての新規性

## 2. デザインシステム構築（トーン 3 案 → 採用 → 同期）

トーンの方向性を 3 案（A: 堅実・金融 = ネイビー高コントラスト / B: モダン SaaS =
ティール・余白広め / C: モノクロ+シグナル = 無彩色 + ステータス色のみ）作り分けて比較し、
**B 案を採用**（理由: 見た目の直感・オーナーのブランド感覚に合う。候補比較はローカル生成
+ ブラウザ比較で実施し、採用結果のみ記録）。

採用トーンをコンポーネントプレビュー 7 点（カラー / タイポ / ボタン / バッジ / テーブル /
カード / サイドバー）に落とし、Claude Code 側から DesignSync ツールで Claude Design の
デザインシステムプロジェクト **settlebase-ds** へ同期した。カード索引が生成されず
Design Systems パネルに表示されない問題があり、カードの明示登録（register）で解決。
トークンの永続版は [design-system.md](../design/design-system.md)。

## 3. 画面要件仕様（screen-specs）と全体感の確定

ワイヤーを描く前に [screen-specs.md](../design/screen-specs.md) を作成し、
画面別の必須要素チェックリスト・ロールモデル 4 種（maker / checker / admin / viewer）を固定。
確認フォームでオーナーの赤入れを取り、全問原案どおり確定した
（ワイヤーの深さ = 主要状態のみ、空状態の描画は台帳のみ）。

並行して「そもそも何のシステムか」の全体感を詰め、[concept.md](../design/concept.md) に固定:

- **すべての残高変動をウォレット間の複式記帳（振替）1 種類に統一**
  （予算配賦 = 準備金→部門 / 立替精算 = 部門→メンバー / 逆仕訳 = 反対振替）
- 残高不足は申請時警告 + 承認時確定、マイナス残高は許容しない
- 承認と同時に自動記帳（1 トランザクション）
- **逆仕訳も申請→承認を通る**（訂正だけが maker-checker をバイパスする穴を作らない）
- 原資はテナント準備金ウォレット（唯一の承認外エントリは開設時の初期化のみ）
- 監査ログは「状態を変えた操作 + ログイン失敗」に限定
  （テナント切替などの閲覧系はアクセスログの領分として対象外）

## 4. ワイヤー生成（Claude Design・プロンプト 7 本）

Claude Design で新規プロジェクトを作成（Design system = settlebase-ds を適用、
Template = Wireframe、1280px デスクトップ固定）。プロンプトは 1 画面 1 本 + 仕上げ 1 本:

1. 共通シェル（テナント切替 + ナビ 7 項目 + ロールバッジ）+ 部門ウォレット
2. 振替・精算申請（冪等キーの説明表示 + 開発者向けキー確認 + 状態バッジ付き申請一覧）
3. 承認（maker-checker: 自分の申請は非活性 + 理由表示、承認は確認ステップ経由）
4. 台帳（append-only: 編集・削除ボタン非存在 + 逆仕訳の相互リンク + 空状態）
5. 監査ログ（操作種別フィルタ + 変更前後の展開表示 + 閲覧専用）
6. ロール管理（変更確認モーダル + 変更理由必須 + 最後の管理者の降格ガード）
7. 台帳のみ仕上げ精度へ（他はワイヤーのまま）

生成物は 1 つのインタラクティブな設計ファイルになり、ナビ切替・承認確認・空状態切替・
逆仕訳リンクのハイライトまで動く状態で出力された。

## 5. 適合チェックと修正（1 往復）

生成された設計ファイルを Claude Code 側から直接読み、screen-specs のチェックリストと
突き合わせて修正 8 点を 1 回の指示にまとめた:

1. **【境界】ダミーメールアドレスに実在ドメインが混入** → example.co.jp へ変更。
   Claude Design がアカウント情報から実在の所属ドメインを拾ったと推定される。
   **「AI が環境から実在情報を拾い込む」実例**であり、公開前チェックを設計段階から
   回すことの価値がそのまま示された
2. 台帳のボタン文言「逆仕訳を作成」→「逆仕訳を申請」（逆仕訳も承認を通る決定の反映）
3. 監査ログからテナント切替（フィルタ・ログ行）を削除（記録対象基準の確定を反映）
4. 部門ウォレット一覧の先頭に準備金ウォレット（バッジ + 「予算配賦の原資」注記）を追加
5. ウォレット作成ボタンに「管理者のみ」注記
6. 立替精算フォームを記帳モデルに整合（費用負担ウォレット選択 + 入金先 = 自分のウォレット固定）
7. 台帳の立替精算行の貸方をメンバーウォレット名に変更
8. ロール管理に「この画面は管理者のみ表示されます」注記

再チェックで 8 点すべての反映を確認した。

## 8. 境界チェック（push 前）

1. 禁止語 grep: repo 全体で 0 件（`grep -rn -e <禁止語リスト> . --exclude-dir=.git --exclude-dir=node_modules`
   にて確認。リスト自体は非公開側で管理）
2. 公開前チェック 4 点: (1) プロンプト・仕様は自作 (2) スクショは自分の環境・自作物のみ
   (3) メンバー投稿・外部やり取りの引用なし (4) 有料コンテンツをなぞっていない — OK
3. PNG 目視: 全 8 枚を確認。人名・部門・金額・メールはすべて架空
   （メールドメインは example.co.jp、§5-1 の混入は修正済み）
4. HTML（ledger.html）: 外部参照・スクリプトなしの自己完結を確認

## 学び

1. **設計ツールにも境界チェックが要る**: AI デザインツールはアカウント情報等の
   実在情報をダミーデータに拾い込むことがある。公開物は生成のたびに禁止語・実在情報の
   チェックを通す（§5-1）
2. **要件の言語化 → 生成 → 適合チェックの型が効く**: チェックリスト付きの仕様
   （screen-specs）を先に固定したことで、生成物の抜け（準備金・監査ログの範囲）を
   機械的に検出でき、修正が 1 往復で済んだ
3. **「すべては振替」の統一が画面を単純にした**: 予算配賦・立替精算・逆仕訳を
   同じ記帳プリミティブに寄せたことで、フォームと台帳の表現が 1 種類で済んでいる
